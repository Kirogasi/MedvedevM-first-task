# ПР №7. AppArmor, Capabilities и Docker

## 1. Linux Capabilities

### Разбор getcap /usr/bin/ping
$ getcap /usr/bin/ping
/usr/bin/ping cap_net_raw=ep

text

**Расшифровка cap_net_raw=ep:**

- **cap_net_raw** - capability, позволяющая процессу использовать сырые (raw) сокеты, необходимо для отправки ICMP-пакетов (ping)
- **e (effective)** - capability активна и проверяется при выполнении операций
- **p (permitted)** - capability разрешена к использованию процессом

### CapPrm / CapEff / CapBnd - в чём разница

| Поле | Название | Описание |
|------|----------|----------|
| CapPrm | Permitted | Набор capabilities, которые процесс может использовать |
| CapEff | Effective | Активные capabilities, проверяемые ядром |
| CapBnd | Bounding | Максимальный набор capabilities, который процесс никогда не сможет получить |

**Дополнительные поля:**
- **CapInh** (Inheritable) - capabilities, которые унаследуют дочерние процессы
- **CapAmb** (Ambient) - набор capabilities, сохраняющихся при смене UID

**Почему лучше чем sudo:**

- При компрометации Python-скрипта злоумышленник не сможет выполнять другие привилегированные операции
- Sudo даёт неограниченные возможности (монтирование ФС, изменение сети и т.д.)

### Флаги e, i, p в cap_net_raw+eip

| Флаг | Название | Значение |
|------|----------|----------|
| e | Effective | Capability активна и используется |
| i | Inheritable | Дочерние процессы могут унаследовать capability |
| p | Permitted | Capability разрешена для использования |

**Отличие ep от eip:**
- `ep` - capability активна только для текущего процесса, дети не наследуют
- `eip` - capability активна, разрешена и будет передана дочерним процессам

| Ресурс | Хост | Контейнер |
|--------|------|-----------|
| Количество процессов | ~300 | 1 |
| Сетевые интерфейсы | eth0, lo, docker0, wlan0 | lo |

### Capabilities: обычный vs --privileged

**Обычный контейнер:**
CapEff = 00000000a80425fb

text

**Расшифровка:**
$ capsh --decode=00000000a80425fb
0x00000000a80425fb = cap_chown,cap_dac_override,cap_fowner,cap_fsetid,cap_kill,cap_setgid,cap_setuid,cap_setpcap,cap_net_bind_service,cap_net_raw,cap_sys_chroot,cap_mknod,cap_audit_write,cap_setfcap

text

**Привилегированный контейнер (--privileged):**
CapEff = 0000003fffffffff

text

**Расшифровка:**
$ capsh --decode=0000003fffffffff
ВСЕ capabilities (полный набор root на хосте)

text

**Чего нет у обычного контейнера:**
- CAP_SYS_ADMIN (администрирование ФС, монтирование)
- CAP_SYS_MODULE (загрузка модулей ядра)
- CAP_SYS_RAWIO (доступ к портам ввода-вывода)
- CAP_SYS_PTRACE (отладка других процессов)
- CAP_NET_ADMIN (управление сетью)
- CAP_SYS_TIME (изменение системного времени)

**Почему --privileged опасен:**
- Даёт контейнеру почти все права root на хосте
- При компрометации контейнера злоумышленник получает полный контроль над хост-системой
- Можно монтировать хостовую ФС, загружать модули ядра, менять сетевые настройки

4. Эшелонированная защита
Слой	Инструмент	Что ограничивает
DAC	chmod/chown	Базовые права на файлы (владелец, группа, остальные)
Capabilities	--cap-drop ALL + cap-add	Отдельные привилегии процессов (сеть, файлы, время)
MAC	AppArmor	Мандатный контроль доступа к файлам и операциям
Изоляция	Docker namespaces	Процессы, сеть, ФС, PID, UTS, IPC - изолированные пространства
Выводы
Capabilities реализуют принцип наименьших привилегий - процесс получает минимально необходимый набор прав.

AppArmor добавляет мандатный контроль доступа, позволяя запрещать операции даже root-процессам.

Docker namespaces обеспечивают изоляцию на уровне ядра: процессы в контейнере не видят процессы хоста и других контейнеров.

Комбинация всех трёх механизмов создаёт глубокоэшелонированную защиту - компрометация одного уровня не даёт полного контроля.

--privileged - антипаттерн в продакшене, дающий контейнеру почти все права хоста.

AppArmor complain mode полезен для отладки профилей - логирует нарушения без блокировки.
## 5. Контрольные вопросы

### Вопрос 1. Чем DAC отличается от MAC? Почему одного DAC недостаточно?

**Ответ:**

| Характеристика | DAC (Discretionary Access Control) | MAC (Mandatory Access Control) |
|----------------|-------------------------------------|--------------------------------|
| Расшифровка | Избирательное управление доступом | Мандатное управление доступом |
| Кто управляет | Владелец ресурса | Система (администратор) |
| Принцип | Владелец сам назначает права | Правила задаются централизованно |
| Примеры | chmod, chown, права rwx | AppArmor, SELinux, SEAndroid |

**Почему одного DAC недостаточно:**

- DAC не защищает от root-процессов - root может игнорировать любые права доступа
- При компрометации программы с UID=0 злоумышленник получает полный контроль над всей системой
- DAC не позволяет ограничить программу в системных вызовах (монтирование ФС, загрузка модулей ядра)
- MAC работает даже для root, запрещая явно разрешённые действия

### Вопрос 2. Что означает запись cap_net_bind_service=eip? Чем ep отличается от eip?

**Ответ:**

**Расшифровка cap_net_bind_service=eip:**

| Флаг | Название | Значение |
|------|----------|----------|
| e | Effective | Capability активна и проверяется ядром |
| i | Inheritable | Дочерние процессы могут унаследовать capability |
| p | Permitted | Capability разрешена для использования |

**Отличие ep от eip:**

| Запись | Значение | Наследование |
|--------|----------|--------------|
| ep | Активна и разрешена только для текущего процесса | Дети НЕ наследуют |
| eip | Активна, разрешена И наследуема | Дети МОГУТ унаследовать |

### Вопрос 3. В чём разница между complain и enforce в AppArmor? Зачем нужен complain?

**Ответ:**

| Режим | Поведение | Логирование | Назначение |
|-------|-----------|-------------|------------|
| complain | Нарушения разрешены, но логируются | Да | Отладка и разработка профилей |
| enforce | Нарушения запрещены и логируются | Да | Боевая эксплуатация |

**Зачем нужен complain:**

- Позволяет тестировать профили без блокировки работы приложений
- Собирает информацию о реальных операциях программы
- Помогает выявить все необходимые разрешения перед включением enforce
- Позволяет постепенно настраивать профиль на работающей системе

### Вопрос 4. Docker использует то же ядро что и хост - почему тогда контейнер изолирован?

**Ответ:**

Изоляция достигается за счёт механизмов ядра Linux:

| Механизм | Что изолирует |
|----------|---------------|
| Namespace (PID) | Процессы - контейнер видит только свои процессы |
| Namespace (NET) | Сеть - отдельный сетевой стек, интерфейсы, маршруты |
| Namespace (MNT) | Файловая система - изолированное дерево каталогов |
| Namespace (UTS) | Имя хоста - свой hostname |
| Namespace (IPC) | Межпроцессное взаимодействие - отдельные очереди сообщений |
| Namespace (USER) | Пользователи - UID/GID могут маппиться на хостовые |
| Cgroups | Ресурсы - ограничение CPU, RAM, I/O |

**Почему изоляция работает:**
- Каждый контейнер имеет собственное пространство имён (namespace)
- Процессы в разных namespaces не видят друг друга
- Ядро проверяет принадлежность к namespace при каждом системном вызове

### Вопрос 5. Злоумышленник нашёл RCE в nginx. Nginx в контейнере без --privileged, с --cap-drop ALL --cap-add NET_BIND_SERVICE, под непривилегированным пользователем, с AppArmor. Что может и не может сделать злоумышленник?

**Ответ:**

**Что НЕ может сделать:**

| Действие | Причина |
|----------|---------|
| Прочитать /etc/shadow хоста | Изоляция ФС (MNT namespace) + AppArmor |
| Монтировать файловые системы | Нет CAP_SYS_ADMIN в capabilities |
| Загрузить модуль ядра | Нет CAP_SYS_MODULE |
| Изменить сетевые настройки | Нет CAP_NET_ADMIN |
| Убить процессы на хосте | Изоляция PID namespace + нет CAP_KILL |
| Выйти из контейнера на хост | Нет привилегированных возможностей |
| Писать в системные директории | DAC права + AppArmor |

**Что МОЖЕТ сделать:**

| Действие | Причина |
|----------|---------|
| Читать/писать внутри контейнера | Базовые права внутри изолированной ФС |
| Отправить сетевые запросы | CAP_NET_RAW не отключена (но нет NET_ADMIN) |
| Попытаться эксплуатировать другие уязвимости | RCE даёт возможность выполнения кода |
| Сканировать порты внутри сети | Доступ к сетевому стеку контейнера |

### Вопрос 6. Почему --privileged - антипаттерн? Когда всё же оправдан?

**Ответ:**

**Почему --privileged - антипаттерн в продакшене:**

| Риск | Описание |
|------|----------|
| Полный root на хосте | Даёт все capabilities, включая CAP_SYS_ADMIN |
| Монтирование хостовой ФС | Возможность читать/писать любые файлы хоста |
| Загрузка модулей ядра | Может скомпрометировать ядро |
| Управление сетью | Может менять настройки сетевых интерфейсов хоста |
| Доступ к устройствам | Прямой доступ к /dev, дискам, памяти |

**Когда оправдан (только в специальных случаях):**

| Сценарий | Причина |
|----------|---------|
| Локальная разработка | Удобство, нет внешних угроз |
| Системные контейнеры | Нужен доступ к устройствам (Docker-in-Docker) |
| Инструменты отладки | strace, gdb, профилирование ядра |
| CI/CD агенты | В полностью доверенной среде |
