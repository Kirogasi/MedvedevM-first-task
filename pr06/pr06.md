# ПР №6. Анализ сетевого трафика: tcpdump и Wireshark

## 1. Разбор строки tcpdump

Строка: `12:34:56.789012 IP 127.0.0.1.44321 > 127.0.0.1.8080: Flags [S], seq 123, length 0`

| Поле | Значение | Что означает |
|------|---------|-------------|
| 12:34:56.789012 | Время захвата | Точное время приёма пакета (часы:минуты:секунды.микросекунды) |
| IP | Протокол | Пакет инкапсулирует IP-дейтаграмму (версия IPv4) |
| 127.0.0.1.44321 | Адрес источника | IP-адрес и порт отправителя (здесь 44321 — временный порт клиента) |
| 127.0.0.1.8080 | Адрес назначения | IP-адрес и порт получателя (8080 — порт HTTP-сервера) |
| Flags [S] | Флаги TCP | SYN-флаг — установка соединения (начало TCP-рукопожатия) |
| seq 123 | Последовательность | Начальный порядковый номер TCP-сегмента (sequence number) |
| length 0 | Длина данных | Размер полезной нагрузки в байтах (0 значит только заголовки) |

## 2. Перехваченные данные HTTP

![Пароль в открытом виде](screens/http-password.png)

**Что видно в трафике:**  
В выводе `tcpdump -A` отчётливо видны строки `username=admin` и `password=supersecret123`, переданные методом POST. Также виден заголовок `Content-Type` и тело запроса целиком.

**Кто в реальной сети может так же прочитать этот трафик:**  
Любой, кто имеет доступ к среде передачи данных: пользователи того же Wi-Fi (при отсутствии шифрования или при использовании общедоступной сети), сотрудник с доступом к коммутатору/маршрутизатору (если настроен порт-мониторинг), злоумышленник с ARP-spoofing'ом в локальной сети, а также провайдер или администраторы сетевого оборудования.

## 3. Follow TCP Stream

![Follow TCP Stream](screens/follow-stream.png)

**Что видит злоумышленник перехвативший этот трафик:**  
Злоумышленник видит полный диалог между клиентом и сервером:  
- **Красным цветом** — запрос клиента: метод POST, путь /login, заголовки (Content-Type, Content-Length, Host) и тело запроса с логином и паролем.  
- **Синим цветом** — ответ сервера (например, код 200 OK или 404 Not Found).  

Становятся известны учётные данные, структура взаимодействия и потенциально сессионные cookie, если они передаются незашифрованными.

## 4. HTTP vs HTTPS — сравнение

| Что наблюдаем | HTTP | HTTPS |
|---|---|---|
| IP-адреса | Видны | Видны (IP-адреса всегда видны, так как это сетевой уровень) |
| Порт назначения | Виден (8080) | Виден (443 для стандартного HTTPS) |
| Заголовки | Видны открытым текстом | Зашифрованы внутри TLS-туннеля (видны только длины и служебные данные TLS) |
| Тело запроса | Видно полностью | Полностью зашифровано |
| Логин/пароль | Видны явно | Не видны (передаются внутри зашифрованного тела) |
| Имя домена | Видно в поле Host | Частично видно через SNI (Server Name Indication), но сам HTTP-запрос зашифрован |

## 5. DNS и приватность

**Какие домены видны в DNS даже при HTTPS:**  
В ходе захвата трафика на порту 53 были видны DNS-запросы к `github.com`, `example.com` и `google.com`. Даже при использовании HTTPS доменные имена утекают через DNS, если не применять DNS-over-HTTPS (DoH) или DNS-over-TLS (DoT).

**Что это означает для приватности:**  
Провайдер или администратор сети видит, какие сайты посещает пользователь, хотя содержимое страниц и передаваемые данные остаются зашифрованными. Это нарушает конфиденциальность факта посещения ресурса.

## 6. Base64

**Декодированная строка:**  
`dmFzeWE6TXlQYXNzd29yZDIwMjQ=` → `vasya:MyPassword2024`

**Почему Base64 не является шифрованием:**  
Base64 — это не шифрование, а способ кодирования двоичных данных в текстовый формат (использует таблицу из 64 символов). Преобразование обратимо без использования какого-либо ключа. Любой, кто перехватит строку `dmFzeWE6TXlQYXNzd29yZDIwMjQ=`, может мгновенно декодировать её обратно в логин и пароль. Для реальной защиты нужно использовать шифрование (TLS) или механизмы с секретным ключом.

## 7. tshark vs tcpdump vs Wireshark

| Инструмент | Когда использовать |
|---|---|
| tcpdump | На сервере без графики, для быстрого захвата, по ssh, в скриптах и автоматизации. Лёгкий, есть везде. |
| tshark | Когда нужны display-фильтры, статистика и анализ протоколов на сервере без GUI. Удобен для автоматизированного разбора pcap-файлов. |
| Wireshark | На рабочей станции с графикой, для глубокого интерактивного анализа, Follow TCP Stream, визуализации, создания фильтров на лету. |

## 8. Каналы утечки через сеть

**Какие меры защиты закрывают сетевой канал утечки:**  
- Использование HTTPS/TLS для шифрования трафика (защита от прослушивания содержимого).  
- VPN (WireGuard, IPsec, OpenVPN) — шифрование всего трафика до выхода в сеть.  
- DNS-over-HTTPS (DoH) / DNS-over-TLS (DoT) — защита DNS-запросов.  
- Сегментация сети и VLAN — ограничение доступа к трафику.  
- Port Security, 802.1X — предотвращение подключения несанкционированных снифферов.  
- Использование шифрованных протоколов поверх SSH-туннелей.  

Ни одна из мер **полностью** не исключает утечку метаданных (IP-адреса, время сессии, объём трафика), но полностью закрывает содержимое.

## Контрольные вопросы

**1. Что такое promiscuous mode и зачем он нужен снифферу?**  
Promiscuous mode (неразборчивый режим) — режим сетевого интерфейса, при котором он принимает все пакеты, проходящие через сегмент сети, а не только адресованные его MAC-адресу. Нужен снифферу, чтобы перехватывать трафик других узлов в широковещательном домене (например, в сети на хабе или при арп-спуфинге). Без этого режима сниффер увидит только трафик, идущий напрямую к его MAC-адресу или широковещательный.

**2. Чем отличается capture filter от display filter в Wireshark?**  
- **Capture filter** задаётся до начала захвата (синтаксис BPF, как в tcpdump) и определяет, какие пакеты **сохранять**, а какие отбрасывать ещё на этапе захвата. Нельзя изменить после начала.  
- **Display filter** применяется уже к захваченным пакетам (синтаксис wireshark-specific, например `http.request.method == "POST"`), только **скрывает/показывает** пакеты из уже имеющегося набора. Можно менять динамически.  

**3. Что такое Follow TCP Stream и для чего используется?**  
Функция Wireshark, которая собирает все TCP-сегменты одного потока (определяемого по комбинации `IP src+port → IP dst+port`) и реконструирует полный диалог в хронологическом порядке, отдельно показывая данные клиента и сервера (красным и синим). Используется для анализа логики приложения, поиска переданных паролей, восстановления переданных файлов, отладки протоколов.

**4. Почему Base64 в HTTP Basic Auth не является защитой? Что нужно использовать вместо?**  
Base64 — это кодировка, не использующая секретный ключ. Преобразование легко обратимо (это не функция шифрования, а отображение байт → текст). HTTP Basic Auth просто оборачивает `login:password` в Base64 и отправляет заголовок `Authorization: Basic ...`. Любой, кто перехватит пакет, декодирует строку за секунду.  
**Вместо этого нужно:**  
- Использовать HTTPS (TLS) — тогда весь заголовок Authorization уйдёт зашифрованным.  
- Или использовать более стойкие методы аутентификации (токены, OAuth 2.0, клиентские сертификаты) поверх TLS.

**5. Какие данные утекают даже при использовании HTTPS? Как это исправить?**  
- IP-адреса источника и назначения (уровень сети — их нельзя скрыть без VPN/Tor)  
- DNS-запросы без DoH/DoT (видно, какие домены посещаются)  
- SNI (Server Name Indication) в TLS-рукопожатии — часто передаёт доменное имя открыто  
- Длины пакетов и временные метки (может допустить частичный анализ)  
- Факт установки HTTPS-соединения и объём переданных данных  

**Как исправить:**  
DoH/DoT для DNS, ECH (Encrypted Client Hello / ранее ESNI) для скрытия SNI, VPN для сокрытия IP-адресов и трафика в целом.

**6. Сисадмин говорит: «у нас свитч, а не хаб — значит сниффинг невозможен». Он прав?**  
Не совсем. В коммутируемой сети (switch) обычный сниффер видит только широковещательный трафик и трафик, адресованный его MAC. Но возможны атаки:  
- ARP-spoofing (отравление ARP-таблицы для перенаправления трафика)  
- Port mirroring (SPAN-port) — если администратор включил зеркалирование порта на порт атакующего  
- MAC flooding (переполнение таблицы коммутации)  
- Внедрение в VLAN.  

Так что сниффинг возможен, но требует дополнительных действий.
